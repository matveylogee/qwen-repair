# M1: Colab feasibility

M1 добавляет реальные интерфейсы inference, изолированного исполнения, LoRA SFT и multi-turn GRPO. Colab передаёт запросы Docker worker на Mac через файловую очередь Google Drive. Первый запуск проверяет только транспорт на CPU. Пройденные проверки и ещё не выполненные удалённые и GPU-запуски перечислены в `docs/m1_validation.md`.

## Среды и версии

Локальный Python-пакет остаётся CPU-совместимым. `qrepair --help`, `doctor` без `--gpu`, работа с данными, Docker и очередь не импортируют torch. Отдельный extra `gpu` закрепляет torch 2.10.0, Transformers 5.20.2, PEFT 0.21.2, TRL 1.16.0, Accelerate 1.11.0 и Datasets 4.7.0. Установка и CPU-интеграция этих версий проверены; совместимость с конкретным Colab runtime подтверждается его preflight.

Qwen и tokenizer закреплены на revision `c1899de289a04d12100db370d81485cdf75e47ca`. Используется `enable_thinking=False`, `trust_remote_code=False`. Счётчики M1 используют настоящие token IDs. Уже сгенерированные токены сохраняются без повторной токенизации; feedback и новое оформление диалога дописываются к существующему префиксу.

Проверенный T4-профиль явно задаёт `float16`. Старый флаг поддержки bf16 в GPU doctor учитывал эмуляцию и не подтверждал нативную поддержку; фактический dtype этого прогона был float16. Теперь GPU doctor, inference и training проверяют нативную поддержку через `including_emulation=False` перед автоматическим выбором dtype; новый GPU doctor на T4 после этой правки ещё не запускался. GPU preflight выполняет маленькое CUDA-умножение и сохраняет GPU/VRAM/CUDA/версии. Наличие установленного torch само по себе не считается GPU-проверкой.

## Локальный Docker

Установите и запустите [Docker Desktop для Mac](https://docs.docker.com/desktop/setup/install/mac-install/). Команды из корня проекта:

```bash
source .venv/bin/activate
python -m pip install -e '.[dev]'
docker pull python@sha256:2d44738ebf4ce5f63b9d9ea871e9c7cfdc0426f7b0c97cac915fd88ded1d86bb
qrepair executor-preflight --config configs/docker_local.yaml --output runs/docker-preflight.json
```

Digest получен после реального pull официального `python:3.13-slim`. Исполнитель требует доступного локального образа с полным digest и успешного preflight. При ошибке он не переключается на выполнение на хосте.

Каждый случай запускается в отдельном контейнере без сети и GPU: непривилегированный UID, read-only root, снятые capabilities, no-new-privileges, seccomp Docker, ограниченные CPU/RAM/PIDs/tmpfs/output/time. Контейнер получает только код кандидата, фиксированный runner и аргументы текущего вызова. Ожидаемые значения и полный test bundle остаются у доверенного supervisor на хосте. Supervisor сравнивает JSON-значения и сам определяет verdict. Строка stdout с `passed` ничего не подтверждает.

Это ограниченный протокол для функций с JSON-входами и выходами. Tuple/set/bytes, нестабильные значения и неподдерживаемые тесты исключаются. Несколько успешных probes не доказывают абсолютную безопасность Docker.

## Файловая очередь через Google Drive

`FileQueueExecutor` использует отдельную папку, реально синхронизируемую между двумя машинами. Вариант: Google Drive для компьютера на Mac и Drive mount в Colab. Сам по себе Drive mount в Colab не синхронизирует произвольный локальный каталог Mac.

На Mac проверьте две отдельные настройки Drive → Settings → Preferences. В `Google Drive` / `Folders from Drive` для My Drive используется `Stream files`; в `Folders from your computer` / `My Mac` Desktop, Documents и каталоги проектов должны быть отключены. Режим Stream относится к My Drive и сам по себе не отключает папки компьютера. Он сохраняет доступ к остальному Drive, поэтому это не изоляция синхронизации одной папкой. Если сейчас выбран Mirror, сначала нужно сохранить и полностью синхронизировать изменения перед сменой режима. [Настройки Google Drive](https://support.google.com/drive/answer/16631477?hl=en).

Перед запуском worker проверьте нагрузку и текущие ошибки Drive. В локальной проверке 4 ноября нагрузка воспроизводилась без worker при накопленном журнале старого зеркалирования. После согласованного переподключения аккаунта журнал очистился, а двухминутная проверка с включённой синхронизацией показала средние 1,76% CPU. Это ограниченное наблюдение; результаты и границы проверки приведены в [m1_validation.md](m1_validation.md).

Если неисправность повторится, используйте штатные шаги Google: Quit/reopen, затем при необходимости Disconnect/reconnect. Перед отключением сохраните важные несинхронизированные изменения и Lost & Found вне Drive: локальные offline-копии и Lost & Found удаляются при отключении. Служебная копия SQLite не сохраняет содержимое файлов. Не редактируйте внутренние базы вручную. [Восстановление Drive](https://support.google.com/drive/answer/2565956?hl=en), [offline-файлы и кеш](https://support.google.com/drive/answer/13470231?hl=en).

Используйте папку `My Drive/qwen-repair-exchange` в том же Drive-аккаунте. Узнайте её полный локальный путь через Finder. На Mac и в Colab выберите один опубликованный commit и новое одинаковое `SESSION_NAME`, например `m1-transport-20261104-01`. Для сессии используется отдельная подпапка `sessions/<SESSION_NAME>`. В терминале Mac задайте реальный путь и имя, затем оставьте один worker работающим:

```bash
source .venv/bin/activate
QREPAIR_EXCHANGE="/полный/локальный/путь/к/qwen-repair-exchange"
SESSION_NAME="m1-transport-20261104-01"
qrepair queue-worker --config configs/docker_local.yaml \
  --queue "$QREPAIR_EXCHANGE/sessions/$SESSION_NAME"
```

Notebook подключает Drive в Colab и создаёт копию `configs/colab_queue.yaml` с `queue_dir: /content/drive/MyDrive/qwen-repair-exchange/sessions/<SESSION_NAME>`. Папка и аккаунт должны совпадать с выбранными на Mac. Новый commit требует обновления обеих сторон и перезапуска worker.

Для первого запуска notebook оставьте `RUN_INFERENCE=False`, `RUN_TRAINING=False` и выберите CPU runtime. Укажите полный 40-символьный `COMMIT_SHA` и имя сессии; после установки и подключения Drive выполняются `executor-preflight` и `executor-probe`. Probe проверяет авторскую задачу в настоящем Docker, GPU и Qwen для него не нужны.

Для самостоятельного CLI-запуска в Colab сначала подключите Drive, создайте копию `configs/colab_queue.yaml` по пути `runs/m1-queue.yaml` и подставьте в неё `queue_dir` выбранной сессии. Проверка связи:

```bash
qrepair doctor --output runs/cpu-preflight.json
qrepair executor-preflight --config runs/m1-queue.yaml --output runs/queue-preflight.json
qrepair executor-probe --config runs/m1-queue.yaml --output runs/queue-probe.json
```

Probe сохраняет round-trip latency отдельно от времени Docker. При отсутствии worker, неверных хешах, старом ответе или превышении deadline обучение не начинается. Если синхронизация слишком медленная, остановитесь на проверке связи и разберите задержку перед дальнейшим RL. Ручной перенос файлов годится для проверки протокола, но не для online обучения.

Протокол использует неизменяемые payload/checksum/READY, идентификаторы run/request/task/policy, хеши кандидата, тестов и лимитов. Worker опрашивает очередь раз в секунду и публикует heartbeat раз в 30 секунд; TTL heartbeat остаётся 120 секунд. По завершении проверки остановите worker через Ctrl+C, чтобы прекратить служебные записи. Worker получает тесты только из своего доверенного registry. Повторная доставка идемпотентна; устаревшие ответы и повреждённые файлы отклоняются. Контрольные суммы обнаруживают повреждение, но не заменяют разграничение доступа к общей папке.

## Notebook и короткое обучение

`notebooks/01_m1_feasibility.ipynb` создаёт отдельный virtualenv через `venv --without-pip`, без запуска `ensurepip`. Системный pip версии 22.3 или новее устанавливает пакет в это окружение через `--python`: базовый пакет по умолчанию, extra `gpu` только при включённых модельных этапах. Этот способ поддерживает окружения, в которых собственного pip нет. [Документация pip](https://pip.pypa.io/en/stable/topics/python-option/). Транспортный запуск заканчивается отчётами CPU doctor, executor preflight/probe и ZIP результатов. Вся логика модели, rewards, masks и checkpoints находится в пакете.

Установка пакетов и GPU-проверка показывают текущий этап, а `run_visible` выводит лог по мере поступления, сохраняя полный текст для результата команды или ошибки. В прежней версии лог появлялся только после завершения subprocess; отсутствие текста само по себе не доказывало зависание. Уже работающую ячейку обновление notebook не изменяет.

При ошибке настройки сохраните полный вывод ячейки. Причина ранее наблюдавшегося `exit 1` при создании окружения в Colab Python 3.13 не установлена: полного stderr не было. Для повторной попытки задайте новые `CHECKOUT_DIR` и `ENV_DIR`, например `/content/qwen-repair-m1-retry1` и `/content/qwen-repair-m1-env-retry1`; старые каталоги не удаляйте.

Три повторных запроса Colab → Drive → Mac Docker прошли: средний round trip 50,68669 с, медиана 47,67209 с. Это короткая проверка обмена, она не доказывает надёжность или пригодность для training. [Подробные измерения](m1_validation.md).

T4 inference уже выполнен: закреплённая Qwen3-0.6B на Tesla T4, float16, Python 3.13.16, CUDA 12.8. Обе попытки `sum_positive` прошли public 2/2 и private 2/2; последняя награда 1, статус `completed`, инфраструктурных ошибок 0. Первая попытка уже правильная: recovery не проверен, одна задача не даёт оценки качества модели. Worker остановлен после пяти запросов: probe и четырёх проверок кандидатов.

Загрузка модели заняла 25,5927 с, генерация 60 токенов 4,1268 с: 14,539 токена/с только во время генерации. Пиковая память, выделенная PyTorch, составила 1,149674 GiB, это не вся занятая память GPU. Полное время по manifest составило 196,6676 с. GPU training и resume ещё не выполнены; пользователь снял паузу для коротких проверок. [Проверенные артефакты](m1_validation.md).

Для отдельного повторения inference задайте `INFERENCE_CONFIG="configs/m1_infer_t4_smoke.yaml"`, `RUN_INFERENCE=True`, `RUN_TRAINING=False`. Профиль содержит одну задачу `sum_positive`, две попытки, `float16` и максимум 512 новых токенов на попытку. Оба флага notebook по умолчанию остаются `False`. При включённом модельном этапе notebook устанавливает `.[gpu]`, выполняет `doctor --gpu` и проверяет транспорт до скачивания весов. Training не включается автоматически.

Следующие команды предназначены для отдельного модельного запуска в GPU-окружении после успешного probe. `runs/m1-queue.yaml` должен указывать на ту же активную сессию Mac worker:

```bash
qrepair doctor --gpu --output runs/gpu-preflight.json
qrepair infer --config configs/m1_infer_t4_smoke.yaml --executor-config runs/m1-queue.yaml --output runs/m1-t4-smoke
qrepair summarize --run runs/m1-t4-smoke
```

Для короткой проверки training используются два шага SFT и два шага GRPO. Пользователь разрешил этот этап. Команды напрямую без persistent-переноса:

```bash
qrepair sft-smoke --config configs/m1_sft.yaml --executor-config runs/m1-queue.yaml --output runs/m1-sft --stop-after 1
qrepair sft-smoke --config configs/m1_sft.yaml --executor-config runs/m1-queue.yaml --output runs/m1-sft --resume-from runs/m1-sft/checkpoint-1
qrepair grpo-smoke --config configs/m1_grpo.yaml --executor-config runs/m1-queue.yaml --output runs/m1-grpo --stop-after 1
qrepair grpo-smoke --config configs/m1_grpo.yaml --executor-config runs/m1-queue.yaml --output runs/m1-grpo --resume-from runs/m1-grpo/checkpoint-1
```

Для самостоятельного CLI-запуска пути в `m1_grpo.yaml` должны указывать на полученный SFT adapter. Notebook задаёт отдельные пути для каждого запуска. Все GPU-команды запускайте в окружении с extra `gpu`.

SFT использует несколько авторских задач: reference и целевой ответ сначала проходят реальные public/private проверки. В recovery-примере feedback получен от настоящего запуска ошибочного кода. Loss применяется только к целевому ответу; prompt, прошлый ошибочный ответ, feedback и padding получают label `-100`.

GRPO запускает стандартный TRL trainer с тонким `rollout_func`. Группа содержит одну задачу, политика не меняется до её завершения, каждый эпизод содержит ровно две попытки. Награда равна private-success последнего кандидата. Ошибка инфраструктуры отменяет группу. `env_mask` исключает feedback и служебные токены из loss; точные token IDs и rollout logprobs сохраняются. Smoke-профиль использует `G=2`, `beta=0`; KL к ошибочному base-model reference не включается молча. Это отдельный диагностический профиль, а не итоговая конфигурация экспериментов.

Checkpoint содержит adapter, optimizer, scheduler, RNG, trainer state, конфигурацию, хеши и completion marker. Resume отвергает неполные или изменённые checkpoints и смену запланированного числа шагов. Каждая CLI-команда создаёт новый процесс. Нулевые rewards и отсутствие дисперсии группы отражаются в отчёте; два выполненных optimizer step не доказывают улучшение модели.

При активном mixed-precision scaler checkpoint также обязан содержать его состояние. После resume `global_step` показывает общий шаг, а время и rollout-счётчики в `training_result.json` относятся к текущему процессу, что отмечено полем `metrics_scope`.

Отчёты всех процессов сохраняются в `segments/`. Поле `optimizer_updates` отделяет попытки optimizer от пропусков scaler и фактических изменений LoRA. `training-audit` проверяет оба сегмента короткого 1+1 прогона, PID процессов, boundary checkpoints и совпадение хеша весов до resume с предыдущим checkpoint. Оно не загружает pickle/torch-объекты. Если все rewards GRPO одинаковы и ненулевого градиента нет, отчёт возвращает `status=plumbing_only`, `passed=false`: работающий цикл ещё не подтверждает обучение. Полный результат экспортируется до этой проверки, чтобы сохранить диагностику.

Notebook ограничивает каждый training-процесс 30 минутами и по умолчанию включает `PERSIST_TRAINING=True`. После первого шага он вызывает `training-export`: один архив, checksum и READY в `MyDrive/qwen-repair-checkpoints/<SESSION_NAME>`, затем `training-import` в новый локальный каталог. Resume использует именно восстановленный checkpoint. Финальные результаты также экспортируются, предыдущие копии сохраняются. Чтение записанного архива через Drive mount проверяет локальную целостность, но не подтверждает завершение фоновой загрузки в облако или успешное восстановление после потери всего runtime.

```bash
qrepair training-export --run runs/m1-sft --destination /путь/к/постоянным/копиям --output runs/sft-transfer.json
qrepair training-import --bundle /путь/из/поля/bundle --output runs/sft-restored
qrepair training-audit --run runs/m1-sft --output runs/sft-audit.json
```

При настоящей потере runtime нужно восстановить тот же commit, GPU-версии и исходные пути, указанные в config (в частности путь SFT adapter для GRPO), затем импортировать архив в новый каталог и выполнить resume. Полностью завершённый двухшаговый checkpoint нельзя продолжать под видом прежнего плана. Проверка отдельного runtime ещё предстоит.

Последняя ячейка создаёт ZIP со всем каталогом запуска, включая созданные checkpoints, и вызывает `google.colab.files.download`. Если браузер блокирует скачивание, сохраните напечатанный ZIP через панель Files. При ошибке транспорта, inference или обучения выполните эту ячейку отдельно для сохранения доступных отчётов. После скачивания остановите worker на Mac, затем завершите runtime.

## Небольшой KodCode-пилот

```bash
python -m pip install -e '.[data]'
qrepair pilot-fetch --output data/kodcode-source --limit 100
qrepair pilot-prepare --source data/kodcode-source --output data/m1-pilot-prepared --max-tasks 10
qrepair pilot-validate --source data/m1-pilot-prepared --output data/m1-pilot-validated --executor-config configs/docker_local.yaml
```

Загрузка закреплена на `dcf78a8bbba9a613b596ce993c4921a38687dfcc`. Поле `conversations` не импортируется. Обработчик принимает только короткие функции и целиком поддерживаемые файлы независимых literal-call assertions. Неподдерживаемые helpers, fixtures и параметризация исключаются, а не тихо теряются. Исходный reference не импортируется на хосте.

Группы определяются до мутаций; M1 использует только предварительную train-область. Public/private cases разделяются целиком, в каждом наборе минимум два случая. В Docker reference проходит оба набора дважды; выбранная AST-мутация должна давать ошибку на обоих. До этого `status=pending_execution_validation` блокирует использование пилота в inference.

Для inference задайте `pilot_dir` в копии `m1_infer.yaml`. Worker файловой очереди должен получить registry этого же пилота через `--registry data/m1-pilot-validated/registry.json`. Короткие SFT/GRPO-команды M1 намеренно используют авторские задачи; массовое обучение и полный аудит KodCode входят в следующие итерации. Глобальный near-duplicate/related-ID аудит ещё не выполнен, пилот не является финальным research split.

После аудита 4 ноября прежний автоматически разделённый пилот не допускается к исследовательской оценке: у части задач private-примеры видны в условии. Для следующей проверки выбран отдельный просмотренный subset, с решениями по всем десяти исходным кандидатам. [Аудит и актуальные пути](data_audit_20261104.md). `load_pilot` теперь проверяет содержимое execution evidence и связь task/code/bundle, а не только наличие файла с контрольной суммой.

Источник и условия использования: [KodCode-Light-RL-10K](https://huggingface.co/datasets/KodCode/KodCode-Light-RL-10K). Локальные данные и результаты исключены из Git.

## Проверенный контракт TRL

В [исходнике TRL v1.16.0](https://github.com/huggingface/trl/blob/v1.16.0/trl/trainer/grpo_trainer.py) `env_mask` из `rollout_func` читается как `tool_mask`, затем умножается на completion mask при вычислении loss. Проверены повторение задач в `RepeatSampler`, группировка rewards и фактический вызов callback. CPU-интеграционный тест проверяет нулевой градиент на токенах окружения и ненулевой на действиях модели. Более ранний или другой TRL не считается совместимым без повторной проверки контракта.
