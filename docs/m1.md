# M1: Colab feasibility

M1 добавляет реальные интерфейсы inference, изолированного исполнения, LoRA SFT и multi-turn GRPO. Команды ограничены короткими проверками. Пройденные проверки и ещё не выполненные GPU-запуски перечислены в `docs/m1_validation.md`.

## Среды и версии

Локальный Python-пакет остаётся CPU-совместимым. `qrepair --help`, `doctor` без `--gpu`, работа с данными, Docker и очередь не импортируют torch. Отдельный extra `gpu` закрепляет torch 2.10.0, Transformers 5.20.2, PEFT 0.21.2, TRL 1.16.0, Accelerate 1.11.0 и Datasets 4.7.0. Установка и CPU-интеграция этих версий проверены; совместимость с конкретным Colab runtime подтверждается его preflight.

Qwen и tokenizer закреплены на revision `c1899de289a04d12100db370d81485cdf75e47ca`. Используется `enable_thinking=False`, `trust_remote_code=False`. Счётчики M1 используют настоящие token IDs. Уже сгенерированные токены сохраняются без повторной токенизации; feedback и новое оформление диалога дописываются к существующему префиксу.

На T4 профиль `dtype: auto` проверяет поддержку bf16 и иначе выбирает fp16. TrainingArguments включает соответствующий режим mixed precision. GPU preflight выполняет маленькое CUDA-умножение и сохраняет GPU/VRAM/CUDA/версии. Наличие установленного torch само по себе не считается GPU-проверкой.

## Локальный Docker

Установите и запустите [Docker Desktop для Mac](https://docs.docker.com/desktop/setup/install/mac-install/). Команды из корня проекта:

```bash
source .venv/bin/activate
python -m pip install -e '.[dev]'
docker pull python@sha256:2d44738ebf4ce5f63b9d9ea871e9c7cfdc0426f7b0c97cac915fd88ded1d86bb
qrepair executor-preflight --config configs/docker_local.yaml --output runs/docker-preflight.json
```

Digest получен после реального pull официального `python:3.13-slim`. Исполнитель требует доступного локального образа с полным digest и успешного preflight. При ошибке он не переключается на выполнение на хосте.

Каждый случай запускается в отдельном контейнере без сети и GPU: непривилегированный UID, read-only root, снятые capabilities, no-new-privileges, seccomp Docker, ограниченные CPU/RAM/PIDs/tmpfs/output/time. Контейнер получает только код кандидата, фиксированный runner и аргументы текущего вызова. Ожидаемые значения и полный test bundle остаются у доверенного supervisor на хосте. Supervisor сравнивает JSON-значения и сам определяет verdict. Строка stdout с `passed` ничего не подтверждает.

Это ограниченный протокол для функций с JSON-входами и выходами. Tuple/set/bytes, нестабильные значения и неподдерживаемые тесты исключаются. Несколько успешных probes не доказывают абсолютную безопасность Docker.

## Связь Mac и Colab

Основной путь M1: модель и trainer в Colab, тесты в Docker на Mac. Для online rollout нужна отдельная папка, реально синхронизируемая между двумя машинами. Вариант: Google Drive для компьютера на Mac и Drive mount в Colab. Сам по себе Drive mount в Colab не синхронизирует произвольный локальный каталог Mac.

Создайте папку `qwen-repair-exchange` в том же Drive-аккаунте. Узнайте её полный локальный путь через Finder. Если общая папка уже настроена, используйте её существующий путь. На Mac и в Colab выберите один commit M1; после обновления кода перезапустите worker. Запустите один worker и оставьте терминал работающим:

```bash
qrepair queue-worker --config configs/docker_local.yaml \
  --queue "/полный/локальный/путь/к/qwen-repair-exchange"
```

В Colab `configs/colab_queue.yaml` указывает на `/content/drive/MyDrive/qwen-repair-exchange`. Если имя/расположение другое, notebook перепишет только `queue_dir` из параметра `QUEUE_DIR`.

Перед скачиванием Qwen notebook проверяет heartbeat worker и выполняет один настоящий запрос:

```bash
qrepair queue-probe --config configs/colab_queue.yaml --output runs/queue-probe.json
```

Probe сохраняет round-trip latency отдельно от времени Docker. При отсутствии worker, неверных хешах, старом ответе или превышении deadline обучение не начинается. Если синхронизация слишком медленная, завершите feasibility и выберите другой транспорт перед дальнейшим RL. Ручной перенос файлов годится для проверки протокола, но не для online обучения.

Протокол использует неизменяемые payload/checksum/READY, идентификаторы run/request/task/policy, хеши кандидата, тестов и лимитов. Worker получает тесты только из своего доверенного registry. Повторная доставка идемпотентна; устаревшие ответы и повреждённые файлы отклоняются. Контрольные суммы обнаруживают повреждение, но не заменяют разграничение доступа к общей папке.

## Notebook и короткое обучение

Откройте `notebooks/01_m1_feasibility.ipynb`, выберите T4, укажите полный commit SHA опубликованной версии M1 и расположение общей папки. Пустой SHA блокирует запуск. Notebook создаёт отдельный virtualenv, выполняет `pip install -e '.[gpu]'`, затем запускает тот же CLI. Вся логика модели, rewards, masks и checkpoints находится в пакете.

Выполняйте ячейки по порядку. GPU doctor проверяет среду; после подключения Drive queue probe проверяет обмен с Mac до загрузки весов Qwen. При повторной настройке выберите новые `CHECKOUT_DIR` и `ENV_DIR`, чтобы не затереть существующее окружение и результаты. Для продолжения обучения в том же runtime используйте ячейки resume, без повторного выполнения установки.

Последовательность команд, которую выполняет notebook:

```bash
qrepair doctor --gpu --output runs/gpu-preflight.json
qrepair queue-probe --config configs/colab_queue.yaml --output runs/queue-probe.json
qrepair infer --config configs/m1_infer.yaml --executor-config configs/colab_queue.yaml --output runs/m1-base
qrepair summarize --run runs/m1-base
qrepair sft-smoke --config configs/m1_sft.yaml --executor-config configs/colab_queue.yaml --output runs/m1-sft --stop-after 1
qrepair sft-smoke --config configs/m1_sft.yaml --executor-config configs/colab_queue.yaml --output runs/m1-sft --resume-from runs/m1-sft/checkpoint-1
qrepair grpo-smoke --config configs/m1_grpo.yaml --executor-config configs/colab_queue.yaml --output runs/m1-grpo --stop-after 1
qrepair grpo-smoke --config configs/m1_grpo.yaml --executor-config configs/colab_queue.yaml --output runs/m1-grpo --resume-from runs/m1-grpo/checkpoint-1
```

Для самостоятельного CLI-запуска пути в `m1_grpo.yaml` должны указывать на полученный SFT adapter. Notebook задаёт отдельные пути для каждого запуска. Все GPU-команды запускайте в окружении с extra `gpu`.

SFT использует несколько авторских задач: reference и целевой ответ сначала проходят реальные public/private проверки. В recovery-примере feedback получен от настоящего запуска ошибочного кода. Loss применяется только к целевому ответу; prompt, прошлый ошибочный ответ, feedback и padding получают label `-100`.

GRPO запускает стандартный TRL trainer с тонким `rollout_func`. Группа содержит одну задачу, политика не меняется до её завершения, каждый эпизод содержит ровно две попытки. Награда равна private-success последнего кандидата. Ошибка инфраструктуры отменяет группу. `env_mask` исключает feedback и служебные токены из loss; точные token IDs и rollout logprobs сохраняются. Smoke-профиль использует `G=2`, `beta=0`; KL к ошибочному base-model reference не включается молча. Это отдельный диагностический профиль, а не итоговая конфигурация экспериментов.

Checkpoint содержит adapter, optimizer, scheduler, RNG, trainer state, конфигурацию, хеши и completion marker. Resume отвергает неполные или изменённые checkpoints и смену запланированного числа шагов. Каждая CLI-команда создаёт новый процесс. Нулевые rewards и отсутствие дисперсии группы отражаются в отчёте; два выполненных optimizer step не доказывают улучшение модели.

При активном mixed-precision scaler checkpoint также обязан содержать его состояние. После resume `global_step` показывает общий шаг, а время и rollout-счётчики в `training_result.json` относятся к текущему процессу, что отмечено полем `metrics_scope`.

Последняя ячейка создаёт ZIP со всем каталогом запуска, включая checkpoints, и вызывает `google.colab.files.download`. Если браузер блокирует скачивание, сохраните напечатанный ZIP через панель Files. При ошибке inference или обучения выполните эту ячейку отдельно для сохранения доступных отчётов. Завершайте runtime после скачивания архива.

## Небольшой KodCode-пилот

```bash
python -m pip install -e '.[data]'
qrepair pilot-fetch --output data/kodcode-source --limit 100
qrepair pilot-prepare --source data/kodcode-source --output data/m1-pilot-prepared --max-tasks 10
qrepair pilot-validate --source data/m1-pilot-prepared --output data/m1-pilot-validated --executor-config configs/docker_local.yaml
```

Загрузка закреплена на `dcf78a8bbba9a613b596ce993c4921a38687dfcc`. Поле `conversations` не импортируется. Обработчик принимает только короткие функции и целиком поддерживаемые файлы независимых literal-call assertions. Неподдерживаемые helpers, fixtures и параметризация исключаются, а не тихо теряются. Исходный reference не импортируется на хосте.

Группы определяются до мутаций; M1 использует только предварительную train-область. Public/private cases разделяются целиком, в каждом наборе минимум два случая. В Docker reference проходит оба набора дважды; выбранная AST-мутация должна давать ошибку на обоих. До этого `status=pending_execution_validation` блокирует использование пилота в inference.

Для inference задайте `pilot_dir` в копии `m1_infer.yaml`. Для очереди локальный worker должен получить registry этого же пилота через `--registry data/m1-pilot-validated/registry.json`. Короткие SFT/GRPO-команды M1 намеренно используют авторские задачи; массовое обучение и полный аудит KodCode входят в следующие итерации. Глобальный near-duplicate/related-ID аудит ещё не выполнен, пилот не является финальным research split.

Источник и условия использования: [KodCode-Light-RL-10K](https://huggingface.co/datasets/KodCode/KodCode-Light-RL-10K). Локальные данные и результаты исключены из Git.

## Проверенный контракт TRL

В [исходнике TRL v1.16.0](https://github.com/huggingface/trl/blob/v1.16.0/trl/trainer/grpo_trainer.py) `env_mask` из `rollout_func` читается как `tool_mask`, затем умножается на completion mask при вычислении loss. Проверены повторение задач в `RepeatSampler`, группировка rewards и фактический вызов callback. CPU-интеграционный тест проверяет нулевой градиент на токенах окружения и ненулевой на действиях модели. Более ранний или другой TRL не считается совместимым без повторной проверки контракта.
