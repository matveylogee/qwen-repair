# TRL сейчас, verl + vLLM как целевой RL backend

Проверка от 4 ноября 2026. Исходная концепция пользователя предполагала verl + vLLM. Бриф предлагал сначала ограниченную проверку Transformers/PEFT/TRL. Реализованный M1 использует стандартный TRL `GRPOTrainer` с `rollout_func`; собственного алгоритма GRPO в репозитории нет. Это промежуточная проверка протокола, а не выполненная интеграция verl.

## Что проверено по исходникам и метаданным

Для конкретного кандидата выбран выпущенный `verl==0.9.1`. Прочитаны метаданные PyPI и файлы `agent_loop.py`, `tool_agent_loop.py`, `ppo_trainer.yaml` из wheel. SHA256 wheel `verl-0.9.1-py3-none-any.whl`: `db6e6f2a8d9d5808d9ec32d357a42319fdc6967df688ff9d9810050f49bfdd14`. Пакет не устанавливался и код wheel не исполнялся.

Это не полный проверенный lockfile: установка, CUDA kernels, LoRA и совместное размещение trainer/rollout на T4 ещё требуют исполнения. Источники: [метаданные verl 0.9.1](https://pypi.org/pypi/verl/0.9.1/json), [метаданные vLLM 0.24.0](https://pypi.org/pypi/vllm/0.24.0/json), [версия verl на PyPI](https://pypi.org/project/verl/0.9.1/).

Наличие одной T4 не является достаточным основанием отказаться от vLLM: T4 есть в списке поддерживаемого оборудования. Но это не доказывает совместимость любой конфигурации verl, attention backend и precision. [Требования vLLM](https://docs.vllm.ai/en/stable/getting_started/installation/gpu/).

## Контракт переноса

У проверенного Agent Loop есть `prompt_ids`, `response_ids`, `response_mask`, `response_logprobs`, `reward_score`. Маска помечает сгенерированные действия единицами, observation и padding нулями. Это соответствует нужному fixed-turn протоколу, но требует нашего отдельного Agent Loop, а не простого переименования `env_mask` из TRL. [Контракт Agent Loop](https://verl.readthedocs.io/en/latest/advance/agent_loop.html).

При переносе сохраняются `PromptView`, две попытки, точные уже сгенерированные token IDs, публичный feedback и terminal reward последнего кандидата. Private tests/reference остаются у evaluator. Каждый reward group содержит одинаковую исходную задачу; веса не меняются до окончания группы. Инфраструктурный сбой отменяет группу. Tool-calling формат нельзя незаметно подставить вместо автоматического исполнения Python-блока.

До замены рабочего backend нужны реальные проверки:

1. Отдельное окружение Python 3.12, согласованные версии и GPU preflight. Существующий runtime TRL сохраняется до окончания его коротких smoke-прогонов.
2. Один Qwen rollout через vLLM в FP16, затем загрузка LoRA; сравнение prompt/token trace с текущим harness.
3. Собственный Agent Loop на том же изолированном executor; две попытки и группа из двух эпизодов. Проверка logprobs и нулевых градиентов на feedback.
4. Один настоящий update с ненулевой дисперсией rewards, обновление LoRA в vLLM, checkpoint и новый процесс resume. Только после этого backend можно называть работающим.

## Что ограничивает скорость сейчас

В первом T4 inference полный прогон занял 196,67 с, генерация 4,13 с, загрузка модели 25,59 с. Замена inference engine ускоряет лишь часть этого времени; существенна задержка файлового executor. На таком запуске нельзя обосновать ускорение всей системы цифрой tokens/sec vLLM. Для масштабирования потребуются измерения групп rollout и транспорта, а не только новая библиотека.

При текущем последовательном GRPO один update с `G=2`, двумя попытками и валидными ответами вызывает шесть executor requests. При измеренном ранее среднем 50,68669 с на round trip иллюстративные 1000 updates дают 84,48 часа только обмена, без GPU-работы. Это не требуемый training budget и не замер будущего запуска. Такой транспорт не следует масштабировать до основного online RL. Батчирование статических проверок и checkpoint cache помогают M1, но не устраняют ожидание feedback внутри rollout.

Для основного RL нужен быстрый канал между GPU и изолированным executor: предпочтительно один управляемый Linux GPU-сервер с проверенным Docker/другим sandbox, либо отдельный executor в той же сети. Drive остаётся хранилищем завершённых checkpoints. Возможность Docker/namespaces на выбранном хостинге нужно проверить до установки модели; наличие GPU само по себе её не гарантирует. Аренда и запуск платного сервера не выполнялись.

Бесплатный Colab не гарантирует ресурсы, длительность и доступность GPU; повторный disconnect не доказывает конкретную причину завершения. Поэтому полноценный RL нельзя планировать как непрерывный многодневный Colab job. Короткий SFT с сохранением состояния и ограниченные экспериментальные запуски остаются отдельными возможностями. [Ограничения Colab](https://research.google.com/colaboratory/faq.html#resource-limits).

Итог spike: совместимый по смыслу Agent Loop существует; для выбранного релиза нужен отдельный Python/ML-профиль. Интеграция и GPU-валидация verl + vLLM остаются отдельным незавершённым этапом. Проверенная математика/masks/resume текущего TRL harness служат эталоном переноса, а не заменяют его.
