# Исполнение Python в Docker

M1 использует установленный пользователем Docker с Linux-контейнерами. Установку Docker Desktop выполняет пользователь. Код кандидата запускается только внутри контейнера. На хосте supervisor передаёт аргументы одного случая и сравнивает JSON-значение с ожидаемым результатом. Полные тесты и ожидаемые значения в контейнер не монтируются.

Поддерживаются только функции с JSON-аргументами и JSON-результатами: None, bool, int, конечные float, str, list и dict со строковыми ключами. Tuple, set, bytes и пользовательские объекты отвергаются. Числа сравниваются по Python `==`, как в исходных поддерживаемых assert; это не универсальный runner произвольных pytest-тестов.

Образ Python необходимо заранее скачать и записать его настоящий digest:

```bash
docker pull python:3.13-slim
docker image inspect python:3.13-slim --format '{{index .RepoDigests 0}}'
```

Полученную строку `python@sha256:...` передают в конфигурацию executor. Код отвергает mutable tags, не скачивает отсутствующие образы и не подставляет выдуманный digest. Требуются рабочие `python`, стандартная библиотека и Linux внутри выбранного образа.

Контейнер запускается с UID/GID 65532, без сети, capabilities и дополнительных привилегий, с read-only root, ограниченными CPU/RAM/PIDs/tmpfs и выводом. Единственный bind mount содержит `solution.py` и runner, доступные только для чтения. Каждый тестовый случай получает новый контейнер. Таймаут исполнения применяется к одному случаю; создание и удаление контейнера имеют отдельный лимит. Не передаются домашний каталог, исходный репозиторий, Docker socket, GPU или переменные окружения хоста.

`DockerExecutor.preflight()` проверяет обычный ответ, бесконечный цикл, переполнение вывода, сеть, host-файл, UID/capabilities/read-only root и лимит процессов. `run()` закрыт до успешной проверки в том же процессе. Ошибка очистки отзывает готовность executor. Успех этих probes не доказывает абсолютную безопасность Docker. Проверки не подтверждены на машине, где Docker отсутствует.

Настоящий интеграционный тест включается явно:

```bash
QREPAIR_TEST_DOCKER_IMAGE='python@sha256:ФАКТИЧЕСКИЙ_DIGEST' python -m pytest tests/test_executor_docker.py -q
```

Остальные executor-тесты проверяют supervisor и протокол очереди с подставными процессами/ответами. Они не подтверждают реальную изоляцию.

Для Colab доступен `FileQueueExecutor`. Локальный worker загружает доверенный registry по bundle ID; запрос не содержит shell-команды или полные тесты. Payload, checksum и финальный READY обязательны для каждого сообщения. Ответ проверяется по request/run/policy/task ID, хешам кандидата, тестов и лимитов. Повторная доставка идемпотентна; истёкший срок, повреждение, отмена и несовместимые лимиты дают `infra_error`.

В пилоте работает один worker. Свежий heartbeat подтверждает успешный preflight и совпадение registry/лимитов; без него клиент отказывается от запуска. Начните с одного запроса и измерьте передачу файлов. Облачная синхронизация может задерживать или переставлять файлы; READY без остальных файлов не считается завершённым сообщением. Не запускайте online RL до проверки реальной синхронизации.

Имя каталога heartbeat имеет вид `<timestamp_ms>-<worker_id>`. Клиент отбрасывает устаревшие записи по имени до чтения файлов и читает максимум две свежие записи каждого worker. Срок действия проверяется после чтения. Старые heartbeat с одним UUID игнорируются; после обновления протокола нужно перезапустить worker.

Worker сохраняет готовый ответ до публикации и повторяет передачу тех же байтов при временном сбое. Существующий неполный или повреждённый ответ не перезаписывается и не вызывает повторное исполнение кандидата. Клиент по-прежнему проверяет checksum, идентификаторы и deadline. Кэш содержит не более 1024 активных запросов; результаты освобождаются по deadline, а последние 1024 завершённых ID позволяют пропускать старые файлы без чтения. Для следующего большого запуска используйте отдельную папку очереди, чтобы старые сообщения не увеличивали стоимость обхода каталога.

Контроллер отвечает за соответствие task ID и bundle ID. Worker проверяет локальный bundle ID и его хеш; task ID служит идентификатором запроса и не является самостоятельным доказательством происхождения задачи. Очередь предполагает выделенную папку с доверенными контроллером и worker; checksums обнаруживают повреждение данных, но не аутентифицируют другой процесс с правом записи.

Параметры контейнера сверены с [Docker run reference](https://docs.docker.com/reference/cli/docker/container/run/).
